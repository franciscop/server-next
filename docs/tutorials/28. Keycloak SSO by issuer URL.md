# Keycloak SSO by issuer URL

The 63 named providers cover the public ones. A self-hosted or per-customer identity server has a different URL for every deployment, so it is configured by that URL instead of a name.

## 1. Point at the realm

```js
import server from '@server/next';

const auth = {
  providers: {
    work: 'https://sso.company.com/realms/employees',
  },
  onLogin: (profile) => upsertUser(profile).id,
  getUser: (id) => db.users.find(id),
};

export default server({ auth });
```

```sh
SECRETS=a-long-random-string
WORK_ID=my-client-id
WORK_SECRET=...
```

**The key name is yours.** `work` names the route (`/auth/login/work`), the environment variables (`WORK_ID`, `WORK_SECRET`) and `profile.provider`. Call it `sso`, `staff` or `company` if that reads better to your users.

Nothing else is needed: the issuer publishes its endpoints at `<issuer>/.well-known/openid-configuration`, and the identity claims in the token become the profile. That is standard OIDC, so the same entry works for Okta, Zitadel, Authentik, FusionAuth, Ory and Microsoft Entra with a tenant URL.

## 2. Two realms, two names

Different populations often live in different realms. They are just two entries:

```js
providers: {
  staff: 'https://sso.company.com/realms/employees',      // STAFF_ID, STAFF_SECRET
  customers: 'https://sso.company.com/realms/customers',  // CUSTOMERS_ID, CUSTOMERS_SECRET
},
```

Two buttons, two routes, and [`ctx.auth.provider`](/documentation/context#ctxauth) tells a handler which one someone came through.

## 3. Groups and roles

Keycloak sends realm roles and groups as non-standard claims, which arrive untouched in `profile.raw`:

```js
  onLogin: (profile) => {
    const groups = profile.raw.groups ?? [];
    const id = upsertUser(profile).id;
    db.users.update(id, { role: groups.includes('admins') ? 'admin' : 'member' });
    return id;
  },
```

Add a mapper in the Keycloak client for whichever claim you want (`groups`, `realm_access.roles`), or it will not be in the token at all.

## 4. Redirect URI

Register `https://your-host/auth/callback/work` as a valid redirect URI on the Keycloak client, matching the name you chose. A mismatch fails at the provider before reaching your app.

## 5. Not to be confused with verifying

This mounts a login: your server sends people to Keycloak and issues its own credential afterwards. If instead a frontend already signed people in and just sends you Keycloak's token, that is the other shape:

```js
const auth = { verify: 'https://sso.company.com/realms/employees', audience: 'my-client-id' };
```

No routes, no client secret, and `ctx.user` is the token's claims. Same server, opposite direction.
