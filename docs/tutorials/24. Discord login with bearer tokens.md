# Discord login with bearer tokens

Cookies are the right default for a server-rendered app. A separate frontend or a native client usually wants to hold the credential itself and send it as a header. That is the `jwt` strategy.

## 1. Switch the strategy

```js
import server from '@server/next';

const auth = {
  providers: 'discord',
  strategy: 'jwt',
  onLogin: (profile) => upsertUser(profile).id,
  getUser: (id) => db.users.find(id),
  toPublicUser: (user) => ({ id: user.id, name: user.name, role: user.role }),
  redirect: '/',
};

export default server({ auth })
  .get('/api/me', (ctx) => ctx.user ?? 401);
```

```sh
SECRETS=a-long-random-string
DISCORD_ID=...
DISCORD_SECRET=...
```

`jwt` signs the person into the token, so no lookup happens per request. `toPublicUser` decides what goes in, and it is required here: whoever holds the token can read it, so never return the whole row.

## 2. Start the login from the client

Ask for the URL instead of following a redirect:

```js
const res = await fetch('/auth/login/discord', {
  headers: { accept: 'application/json' },
});
const { url } = await res.json();
location.href = url;
```

`Accept: application/json` is what turns the `302` into `{ url }`. Same route, same app: the caller decides.

## 3. Collect the token

Discord sends the browser back to `/auth/callback/discord`, which the framework mounts. It redirects to your `redirect` target with the token in the URL **fragment**:

```
https://example.com/#token=eyJhbGciOi...
```

A fragment rather than a query string, because browsers never send it to a server: it stays out of access logs and referrer headers.

```js
const params = new URLSearchParams(location.hash.slice(1));
if (params.get('token')) {
  localStorage.token = params.get('token');
  history.replaceState(null, '', location.pathname);
}
```

Then send it on every call:

```js
fetch('/api/me', { headers: { authorization: `Bearer ${localStorage.token}` } });
```

## 4. Native apps

Open the **system browser** at `/auth/login/discord` rather than fetching the URL from the app's own HTTP client.

The CSRF state is a short-lived cookie, and it has to land in the jar the browser presents at the callback. Fetching from the app puts it in the app's jar instead, and the callback then fails with a `403`. Opening the system browser is also the platform-recommended flow (`ASWebAuthenticationSession`, Custom Tabs), so this is not a workaround.

## 5. Revoking

A signed token cannot be taken back: it is valid until it expires. Keep `expires` short if that matters:

```js
const auth = { providers: 'discord', strategy: 'jwt', expires: '1h', /* ... */ };
```

If you need to end a session on demand, use `session` or `token`, where the credential is an id you can delete. See [revocable sessions](/tutorials/23-revocable-sessions-in-postgres).

## 6. Serving a browser app and an API at once

Accept either credential, and issue the first on login:

```js
const auth = { providers: 'discord', strategy: ['session', 'jwt'], /* ... */ };
```

[`ctx.auth.strategy`](/documentation/context#ctxauth) then tells a handler how the current request authenticated.
