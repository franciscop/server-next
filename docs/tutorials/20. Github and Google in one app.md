# Github and Google in one app

Letting people choose how they sign in, and landing them on the same account when they choose differently next time.

## 1. Name them

```js
import server from '@server/next';

const auth = {
  providers: ['github', 'google'],
  onLogin,
  getUser,
};

export default server({ auth });
```

```sh
SECRETS=a-long-random-string
GITHUB_ID=...   GITHUB_SECRET=...
GOOGLE_ID=...   GOOGLE_SECRET=...
```

Each name mounts its own routes, so the buttons are two links:

```html
<a href="/auth/login/github">Continue with GitHub</a>
<a href="/auth/login/google">Continue with Google</a>
```

Every provider reads `<NAME>_ID` and `<NAME>_SECRET`, and the name you write is the name in the route. There are [63 to choose from](/documentation/authentication#the-providers).

## 2. One account, either provider

The profile is normalised, so `onLogin` does not care which one it came from. Matching on email is what merges them:

```js
const onLogin = (profile) => {
  db.run(
    `INSERT INTO users (id, email, name, avatar)
     VALUES (?1, ?2, ?3, ?4)
     ON CONFLICT(email) DO UPDATE SET name = ?3, avatar = ?4`,
    [crypto.randomUUID(), profile.email, profile.name, profile.avatar],
  );
  return db.query('SELECT id FROM users WHERE email = ?').get(profile.email).id;
};
```

Sign in with GitHub today and Google tomorrow, same address, same row, same id in the cookie.

## 3. Record which ones are linked

`profile.provider` says which was used, so you can keep a column per provider and show "connected accounts" in settings:

```js
db.run(`ALTER TABLE users ADD COLUMN github_id TEXT`);
db.run(`ALTER TABLE users ADD COLUMN google_id TEXT`);

const onLogin = (profile) => {
  const id = upsertByEmail(profile);
  db.run(`UPDATE users SET ${profile.provider}_id = ? WHERE id = ?`, [profile.id, id]);
  return id;
};
```

Interpolating `profile.provider` into SQL is only safe because the provider list is a fixed literal in your config. It never contains user input, and a column name cannot be a bound parameter, so keep that list closed.

## 4. Which one is this request

Which provider signed someone in is on [`ctx.auth`](/documentation/context#ctxauth), not on the user, because it describes the login rather than the person:

```js
  .get('/me', (ctx) => {
    if (!ctx.user) return 401;
    return { ...ctx.user, signedInWith: ctx.auth.provider };
  })
```

## 5. The caveat that matters

Matching on email means trusting the provider to have verified it. GitHub and Google only return addresses they own, so this is safe for both.

Adding a provider that hands back unverified emails changes that: someone could register your address there and take the account. Before merging on email, check that provider's own verification flag in `profile.raw`, or key the account on `profile.provider` plus `profile.id` instead and offer linking as an explicit action in settings.
