# Clerk tokens in a same-origin cookie

Clerk hosts the sign-in UI and owns the user database. Your server mounts nothing: it verifies the session token Clerk issues, which for a same-origin app arrives in a cookie rather than a header.

## 1. Read their cookie

```js
import server from '@server/next';

export default server({ auth: 'cookie:clerk' })
  .get('/', (ctx) => ctx.user ? `Hello ${ctx.user.sub}` : 'Signed out');
```

```sh
CLERK_ISSUER=https://touched-donkey-12.clerk.accounts.dev
CLERK_AUDIENCE=https://app.example.com
```

Clerk's frontend SDK stores the token in a `__session` cookie on your domain, so a plain page navigation carries it. Nothing needs to attach a header.

For a native or cross-origin client, use `jwt:clerk` and send `Authorization: Bearer <token>` instead. Same verification either way; only the carrier changes.

## 2. The part people get wrong

**Clerk session tokens carry no `aud` claim at all.** The authorized party, your frontend origin, is in `azp`, which is what Clerk's own backend SDK checks.

So `CLERK_AUDIENCE` is your app's origin (`https://app.example.com`), not an API identifier as it would be for Auth0. Set it to an API identifier and every token is rejected with a plain `401` that says nothing about which claim failed. The shorthand handles this by setting `audienceClaim: 'azp'` for you; written out it is:

```js
const auth = {
  verify: process.env.CLERK_ISSUER,
  audience: 'https://app.example.com',
  audienceClaim: 'azp',
  cookie: '__session',
};
```

## 3. Your own users

`ctx.user` is the claims by default: `sub` (Clerk's user id), `sid`, `azp` and whatever you add in their dashboard. Once you need a table of your own, map it:

```js
const auth = {
  verify: process.env.CLERK_ISSUER,
  audience: process.env.CLERK_AUDIENCE,
  audienceClaim: 'azp',
  cookie: '__session',
  getUser: (id) => db.users.byClerkId(id),   // `id` is the `sub` claim
};
```

Create that row on Clerk's `user.created` webhook so your table stays in step with theirs, and treat their id as the foreign key rather than the email, which people change.

## 4. Signing out

Clerk's frontend SDK clears its own cookie; there is nothing of ours to clear, and `POST /auth/logout` is not mounted here. Whatever the token's lifetime is in the Clerk dashboard is how long it stays valid.
