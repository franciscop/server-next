# Supabase tokens with your own users

Supabase Auth signs people in from the browser and hands them a JWT. Your server runs no login: it checks the token that arrives on every request, then maps it to a row of yours.

## 1. Verify the token

```js
import server from '@server/next';

export default server({ auth: 'jwt:supabase' })
  .get('/api/me', (ctx) => ctx.user ?? 401);
```

```sh
SUPABASE_ISSUER=https://xyzcompany.supabase.co/auth/v1
SUPABASE_AUDIENCE=authenticated
```

No routes are mounted and no client secret is needed. The issuer publishes its public keys; they are fetched once and cached by key id.

`audience` is the literal string `authenticated`. It is the Postgres role Supabase puts in the token, identical for every project, not something from your dashboard.

## 2. Send it from the browser

```js
const { data } = await supabase.auth.getSession();

await fetch('/api/me', {
  headers: { authorization: `Bearer ${data.session.access_token}` },
});
```

## 3. Claims are not a user row

Out of the box `ctx.user` is the token's claims: `sub`, `email`, `role`, `app_metadata`. That is enough for a claim check:

```js
  .get('/admin', (ctx) => {
    if (!ctx.user) return 401;
    // app_metadata is server-controlled; user_metadata is editable by the user
    if (ctx.user.app_metadata?.role !== 'admin') return 403;
    return db.reports.all();
  })
```

But there is no id of yours in it, so ownership checks have nothing to compare against.

## 4. Map to your own table

`getUser` means the same thing here as everywhere: turn an id into a person. The id is the `sub` claim, which is Supabase's user id:

```js
const auth = {
  verify: process.env.SUPABASE_ISSUER,
  audience: 'authenticated',
  getUser: (id) => db.users.bySupabaseId(id),
};

export default server({ auth })
  .get('/files/:id', async (ctx) => {
    if (!ctx.user) return 401;
    const file = await db.files.find(ctx.url.params.id);
    if (!file) return 404;
    if (file.userId !== ctx.user.id) return 403;
    return file;
  });
```

`ctx.user` is now your record, and the handler reads exactly as it would under any other setup. Create the row the first time you see a `sub` you do not know, or on Supabase's own webhook.

## 5. Why the audience is required

One issuer serves many applications, all signed with the same keys. A token minted for another one carries a valid signature and the same `iss`, so the audience is the only claim separating them. That is why it has no default.
