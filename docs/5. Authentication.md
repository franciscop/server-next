# Authentication

Set the `auth` option and every request gets [`ctx.user`](/documentation/context#ctxuser): the signed-in person, or `undefined`. It never blocks a request on its own, so what each person may do is [authorization](/documentation/concepts#authorization), plain `if` statements in your handlers.

## Signing in with GitHub

```jsx
// index.js
import server from "@server/next";

export default server({ auth: 'cookie:github' })
  .get('/', (ctx) => {
    if (!ctx.user) return <a href="/auth/login/github">Sign in with GitHub</a>;
    return (
      <form method="POST" action="/auth/logout">
        Hello {ctx.user.name} <button>Log out</button>
      </form>
    );
  });
```

```sh
# .env
SECRETS=a-long-random-string
GITHUB_CLIENT_ID=...
GITHUB_CLIENT_SECRET=...
```

Get the two GitHub values by creating an OAuth app at [github.com/settings/developers](https://github.com/settings/developers), with the callback URL set to `http://localhost:3000/auth/callback/github`. The [Sign in with GitHub using OAuth](/tutorials/b-sign-in-with-github-using-oauth) tutorial walks through it step by step.

`'cookie:github'` reads as "sign in with GitHub, stay signed in with a cookie". It mounts the [login routes](#routes), and signs the person's `id`, `email`, `name` and `avatar` into an `HttpOnly` cookie, so there is no database to set up.

## Protecting routes

Check `ctx.user` where it matters:

```js
.get('/account', (ctx) => {
  if (!ctx.user) return 401;
  return `Hello ${ctx.user.email}`;
})
```

Roles, ownership checks and upload routes are covered in [Authorization](/documentation/concepts#authorization).

## A login flow with your database

To keep your own users (roles, settings, signing someone out everywhere), add two callbacks: `onLogin` stores whoever just signed in, and `getUser` reads them back.

```js
const auth = {
  providers: 'github',
  onLogin: async (profile) => {
    const user = await db.users.upsert({ email: profile.email });
    return user.id;                        // what the credential points at
  },
  getUser: (id) => db.users.find(id),      // the user, from that id
};

export default server({ auth })
  .get('/me', (ctx) => ctx.user);          // your own row
```

| Key | Type | Required, or default |
|-----|------|----------------------|
| [`providers`](#providers) | `string`, `string[]` or an object | required |
| [`strategy`](#strategies) | `'session' \| 'cookie' \| 'token' \| 'jwt'` | `'session'` |
| [`expires`](#expires) | duration | `'30d'` |
| [`onLogin`](#onlogin) | `(profile, ctx) => id` | with `getUser` |
| [`getUser`](#getuser) | `(id, ctx) => user` | always for `session` and `token` |
| [`toPublicUser`](#topublicuser) | `(user) => publicUser` | with `getUser`, for `cookie` and `jwt` |
| [`onLogout`](#onlogout) | `(id, ctx) => void` | none |
| [`redirect`](#redirect) | string, function, or an object | `'/'` |

Without callbacks only `cookie` and `jwt` work, since they sign the whole profile into the credential. `session` and `token` carry an id, so they need `getUser` to read it back.

### onLogin

Runs once per login, with the [profile](#the-profile) and the request. Return the id the credential should point at, or throw a [`ServerError`](/documentation/errors#throwing-your-own) to refuse:

```js
import { ServerError } from "@server/next";

onLogin: async (profile, ctx) => {
  const existing = await db.users.find({ email: profile.email });
  if (existing?.banned) throw new ServerError('ACCOUNT_SUSPENDED', 403);
  await db.carts.move(ctx.cookies.cart, existing?.id);    // merge anonymous state
  const user = await db.users.upsert(
    { email: profile.email },
    { [`${profile.provider}Id`]: profile.id, name: profile.name },
  );
  return user.id;
},
```

A refused visitor lands on [`redirect.error`](#redirect) with the code, `?error=ACCOUNT_SUSPENDED`, and that page turns it into words. Only codes travel in the URL, never text:

| `?error=` | When |
|-----------|------|
| your `ServerError`'s code | `onLogin` refused them |
| `ACCESS_DENIED` (or another OAuth code) | they cancelled at the provider |
| `LOGIN_FAILED` | anything else: a bug, the provider down. It is logged |

Show a generic message for any code you do not recognise.

`profile.provider` says which provider this login came through, so whether a GitHub and a Google login with the same email share a row is up to your query.

#### One row per login

Return a session id instead of a user id and every login gets its own row, which people can list and end:

```js
onLogin: async (profile, ctx) => {
  const user = await db.users.upsert({ email: profile.email });
  const session = await db.sessions.create({
    userId: user.id,
    userAgent: ctx.headers['user-agent'],
  });
  return session.id;
},
getUser: (id) => db.sessions.findUser(id),      // joins back through userId
onLogout: (id) => db.sessions.delete(id),
```

### The profile

The same shape from every provider:

```ts
{
  provider: 'github',
  id: '583231',
  email, name, avatar,
  accessToken, refreshToken?,
  raw,             // the untouched response, for provider-specific fields
}
```

Anything outside that set is in `raw`: a GitHub `company`, a Keycloak `groups` claim, a Google `hd` domain.

Store `accessToken` in `onLogin` to call the provider's API on their behalf later, with the [`scopes`](#providers) you asked for:

```js
const auth = {
  providers: { github: { scopes: ['repo'] } },
  onLogin: async (profile) => {
    const user = await db.users.upsert({ email: profile.email });
    await db.tokens.set(user.id, profile.accessToken);
    return user.id;
  },
  getUser: (id) => db.users.find(id),
};
```

### getUser

Turns the id from `onLogin` into the user, which becomes `ctx.user`:

```js
getUser: (id, ctx) => db.users.find(id),
```

Under `session` and `token` it runs on every request, so a changed role applies on the next one. Return `undefined` and that credential is signed out: deleting the row (or the session) revokes the login. Under `cookie` and `jwt` it runs once, at login, feeding `toPublicUser`.

### toPublicUser

For `cookie` and `jwt`, which sign the user into the credential. It picks what gets signed, which is what `ctx.user` is on later requests and what the client can read:

```js
toPublicUser: (user) => ({ id: user.id, email: user.email, role: user.role }),
```

It is required with `getUser` under those two strategies, so the whole row is never signed by accident.

### onLogout

Runs on `POST /auth/logout` with the same id `getUser` receives. The credential is cleared either way; this is where you end it on the server too:

```js
onLogout: (id) => db.sessions.delete(id),                 // this login
onLogout: async (id) => {                                 // every login
  const session = await db.sessions.find(id);
  if (session) await db.sessions.deleteAll(session.userId);
},
```

Without it, a copy of the credential taken before logging out keeps working until it expires. Under `jwt` that is always the case, since a token is checked by its signature alone.

### redirect

```js
redirect: '/app',
redirect: (user) => (user.role === 'admin' ? '/admin' : '/app'),
redirect: {
  login: '/app',
  logout: '/',
  error: '/login?failed',
},
```

A bare string or function sets `login` only. Never build the target from request input: under `jwt` the redirect carries the token, so an attacker-chosen target sends it off-site.

## Strategies

Where the credential rides, and what it holds:

| `strategy` | Carried in | Holds | Per request | What logout invalidates |
|-----------|------------|-------|-------------|-------------------------|
| `'session'` | a cookie | an opaque id | `getUser(id)` | whatever `onLogout` deletes |
| `'cookie'` | a cookie | signed user data | nothing | this browser only |
| `'token'` | `Authorization` | an opaque id | `getUser(id)` | whatever `onLogout` deletes |
| `'jwt'` | `Authorization` | signed user data | nothing | nothing, the client drops it |

- `'session'`: browser, and the server remembers
- `'cookie'`: browser, and the server forgets
- `'token'`: API client, and the server remembers
- `'jwt'`: API client, and the server forgets

The cookie strategies need the frontend and the API on the same site (`app.example.com` calling `api.example.com` is fine): the cookie is `SameSite=Lax`, so browsers do not send it on requests from another domain. For a frontend on a different domain, use `token` or `jwt`.

### expires

```js
expires: '30d',    // s, m, h, d, w
```

How long a credential stays valid, from when it was issued.

## Providers

Name the providers people can sign in with. Email and password is out of scope; for that, pass a [Better Auth](#a-library) instance instead.

Three spellings, from shortest to most explicit:

```js
providers: 'github',
providers: ['github', 'google'],
providers: { github: {}, google: {} },
```

The object form is the one that takes settings, and a bare string value is shorthand for an [issuer](#any-oidc-issuer):

```js
providers: {
  github: { scopes: ['repo'] },
  google: { prompt: 'consent' },
  work: 'https://keycloak.company.com/realms/main',
},
```

| Key | Meaning | Default |
|-----|---------|---------|
| `clientId` | OAuth client ID | `<PROVIDER>_CLIENT_ID` from the environment |
| `clientSecret` | OAuth client secret | `<PROVIDER>_CLIENT_SECRET` from the environment |
| `scopes` | string or array of strings | the provider's own |
| `issuer` | an OIDC issuer URL | none |
| anything else | passed through to the authorize URL | |

Passthrough is how `prompt`, `team` and `tenant` work without the framework knowing they exist.

**For an issuer of your own, the key name is yours**, and it drives three things at once: the route (`/auth/login/work`), the environment variables (`WORK_CLIENT_ID`, `WORK_CLIENT_SECRET`), and `profile.provider`, which is what `onLogin` branches on. So two issuers is just two names:

```js
providers: {
  staff: 'https://auth.example.com/realms/employees',       // STAFF_CLIENT_ID, ...
  customers: 'https://auth.example.com/realms/customers',   // CUSTOMERS_CLIENT_ID, ...
},
```

### Any OIDC issuer

A provider we do not ship, or a tenant-specific one (Keycloak realms, self-hosted Authentik, a private Okta), takes an issuer URL instead. It publishes everything needed at `<issuer>/.well-known/openid-configuration`, so there is nothing else to configure:

```js
providers: { work: 'https://keycloak.company.com/realms/main' },   // WORK_CLIENT_ID, ...
```

Claims outside the standard set, like group memberships or a namespaced role, arrive in [`profile.raw`](#the-profile).

## Checking a token minted elsewhere

When another service signed the person in (Clerk, Supabase, Firebase, Auth0...), its SDK sends a token with every request and there is nothing to mount. Point at the issuer and say who the token is for:

```js
const auth = { issuer: 'https://xyz.supabase.co/auth/v1', audience: 'authenticated' };

export default server({ auth })
  .get('/me', (ctx) => ctx.user);      // the token's claims
```

| Issuer | `issuer` | `audience` |
|--------|----------|------------|
| Supabase | `https://<ref>.supabase.co/auth/v1` | `authenticated` |
| Auth0 | `https://<tenant>.auth0.com/` | your API identifier |
| Cognito | `https://cognito-idp.<region>.amazonaws.com/<pool>` | the app client id |
| Clerk | `https://<slug>.clerk.accounts.dev` | your frontend API |
| Keycloak | `https://<host>/realms/<realm>` | the client id |
| Google | `https://accounts.google.com` | your OAuth client id |

| Key | Type | Required, or default |
|-----|------|----------------------|
| `issuer` | issuer URL | required |
| `audience` | string or array of strings | required |
| `cookie` | string | none: reads `Authorization: Bearer` |
| `audienceClaim` | string or array of strings | `'aud'` |
| `getUser` | `(id, ctx) => user` | none: `ctx.user` is the claims |

Every request checks the signature against the issuer's published keys (fetched once, and again when they rotate), plus `iss`, `aud` and the expiry. `audience` is required because other apps on the same issuer get validly signed tokens too, and the audience is what tells yours apart.

Some issuers put the audience in another claim. Name it with `audienceClaim`; with a list, the first claim present wins:

```js
const auth = { issuer: ISSUER, audience: 'https://app.example.com', audienceClaim: 'azp' };
```

### By name

Clerk, Supabase and Firebase have a shorthand, with the issuer and audience in the environment:

```js
const auth = 'jwt:clerk';      // Authorization: Bearer, for a native or cross-origin client
const auth = 'cookie:clerk';   // their __session cookie, for a same-origin app
```

```sh
CLERK_ISSUER=https://<slug>.clerk.accounts.dev
CLERK_AUDIENCE=https://app.example.com
```

Both variables are required, and a missing one is a boot error naming it. Only `jwt:` and `cookie:` apply, since `session:` and `token:` need a `getUser` of yours to resolve an id.

| Name | `<NAME>_ISSUER` | `<NAME>_AUDIENCE` | Claim | Cookie |
|------|-----------------|-------------------|-------|--------|
| `clerk` | `https://<slug>.clerk.accounts.dev` | your frontend origin | `azp` | `__session` |
| `supabase` | `https://<ref>.supabase.co/auth/v1` | `authenticated` | `aud` | none |
| `firebase` | `https://securetoken.google.com/<project>` | the project id | `aud` | none |
| `gcip` | `https://securetoken.google.com/<project>` | the project id | `aud` | none |

The easy mistakes:

- **Clerk** tokens have no `aud`. The audience is your frontend origin, checked against `azp`; an API identifier, as you would use for Auth0, rejects every token.
- **Supabase**'s audience is the literal `authenticated`, the same for every project.
- **Firebase** puts the project id in both: the issuer ends in `/<project>` and the audience is `<project>`. `gcip` is the same service under its Google Cloud name. Neither is [`google`](#the-providers): a Firebase `sub` is a Firebase uid, and `firebase.sign_in_provider` says how they signed in.
- **Auth0, Cognito and Keycloak** use the long form, since their names already mean the [login providers](#the-providers):

```js
const auth = { issuer: 'https://acme.auth0.com/', audience: 'https://api.example.com' };
const auth = { issuer: COGNITO_POOL_URL, audience: CLIENT_ID, audienceClaim: ['aud', 'client_id'] };
```

"Cookie" is where the vendor's SDK keeps the token for a same-origin app. With none, the client sends it as a header and only `jwt:` applies. To read another cookie, use the long form:

```js
const auth = {
  issuer: process.env.SUPABASE_ISSUER,
  audience: 'authenticated',
  cookie: 'sb-xyz-auth-token',
};
```

### Your own row

Without `getUser`, `ctx.user` is the token's claims: `sub`, `email`, and whatever else the issuer includes, but no role column of yours. Add `getUser` to turn the `sub` claim into your own user:

```js
const auth = {
  issuer: 'https://xyz.supabase.co/auth/v1',
  audience: 'authenticated',
  getUser: (id, ctx) => db.users.byExternalId(id),
};
```

## A function

For API keys, or any check you want to write yourself:

```js
const auth = (ctx) => db.users.byApiKey(ctx.headers['x-api-key']);
```

It runs at most once per request, and `ctx.user` is typed as whatever it returns. Return `undefined` for "not signed in"; to fail the request instead, throw:

```js
throw new ServerError('AUTH_EXPIRED_TOKEN', 401, 'Your session expired');
```

## A library

Libraries that run their own sign-in, like [Better Auth](https://www.better-auth.com), take the instance. This is also the way to email and password sign-in:

```js
const auth = betterAuth({ database, socialProviders: { github } });

export default server({ auth });
```

Its routes are mounted under its own prefix and reach it with the body unread, and `ctx.user` comes from its session.

## ctx.auth

Next to `ctx.user`, `ctx.auth` describes the credential itself, read straight from it:

```ts
ctx.auth   // { issuedAt: Date, expiresAt?: Date, strategy?, provider? }
```

`provider` is who they signed in with, and `strategy` is how this request authenticated. Use `issuedAt` to ask for a fresh sign-in before something irreversible (see [Sensitive actions](/documentation/concepts#sensitive-actions)). It is `undefined` when there is no credential, and for the [function](#a-function) and [library](#a-library) shapes.

## Typing ctx.user

`ctx.user` is typed from your own `auth`, so an app never declares a `User` type:

```ts
server({ auth: { providers: 'github', onLogin, getUser: (id) => db.users.find(id) } })
  .get('/admin', (ctx) => {
    if (!ctx.user) return 401;
    ctx.user.role;      // typed from getUser's return
    ctx.user.plan;      // compile error
  });
```

| `auth` | `ctx.user` |
|--------|------------|
| a login flow with `getUser` | `getUser`'s return |
| a login flow without callbacks, or the string form | the [profile](#the-profile) |
| `{ issuer, audience }` with `getUser` | `getUser`'s return |
| `{ issuer, audience }` alone | the token's claims |
| a function | its return |

It is always possibly `undefined`, since that is what being signed out means, so it has to be checked before use.

For handlers and middleware in **other files**, there is no `server()` call to infer from, so declare it there instead:

```ts
import { router, type Middleware } from "@server/next";

const requireAdmin: Middleware<{ user: User }> = (ctx) => { ... };
export default router<{ user: User }>().get('/admin', (ctx) => ctx.user.role);
```

## Routes

Mounted only by a login flow:

| Method | Route | Does |
|--------|-------|------|
| `GET` | `/auth/login/<provider>` | starts the handshake |
| `GET` | `/auth/callback/<provider>` | finishes it, calls `onLogin`, issues the credential |
| `POST` | `/auth/logout` | calls `onLogout`, clears the credential |

CSRF protection is built in: a short-lived `HttpOnly` cookie ties the callback to the browser that started the login. A same-origin `fetch('/auth/login/github')` works as is. A **native app must open `/auth/login/<provider>` in the system browser** rather than fetch it, or the cookie lands in the app's own jar and the callback fails with a `403`.

A script that sends `Accept: application/json` to `/auth/login/<provider>` gets the provider's URL instead of a redirect, to send the person there itself:

```json
{ "url": "https://github.com/login/oauth/authorize?client_id=..." }
```

Under `session` and `cookie` the callback sets the cookie and redirects to `redirect.login`. Under `token` and `jwt` it redirects with the credential in the URL fragment, which never reaches a server log:

```
https://example.com/app#token=eyJhbGciOi...
```

The fragment does stay in the browser's history, so read it and clear it as soon as the page loads:

```js
const token = new URLSearchParams(location.hash.slice(1)).get('token');
history.replaceState(null, '', location.pathname + location.search);
```

A native app sets [`redirect.login`](#redirect) to its own scheme, `redirect: 'myapp://signed-in'`, and the system browser hands `myapp://signed-in#token=...` straight back to the app.

## Responses

| Situation | Status |
|-----------|--------|
| No credential | anonymous (`ctx.user` is `undefined`) |
| Unknown or expired id | anonymous (`ctx.user` is `undefined`) |
| A tampered or expired cookie | anonymous, and the cookie is cleared so the next request starts clean. With [`log`](/documentation/options#optionslog) on, it says why |
| A tampered or expired bearer token | `401`: it was attached deliberately, so the client must be told |
| An `Authorization` header with another scheme | ignored: not ours to police |
| A token from the wrong issuer or audience | `401` |
| Failed OAuth `state` check, or none sent | `403` |
| A callback with no `code` | `400` |
| The login failed | a redirect to `redirect.error` with `?error=CODE`: a thrown `ServerError`'s code, the provider's own (`ACCESS_DENIED`), or `LOGIN_FAILED` |
