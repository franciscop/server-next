# Authentication

The [`auth` option](#optionsauth) registers the login [routes](#routes) and populates [`ctx.user`](#ctxuser) on every request. It never blocks a request on its own (see [Protecting routes](#protecting-routes)).

```js
server({ auth: 'cookie:github' });
server({ auth: { ...authOptions }});
```

For a step-by-step setup, see the [Login with GitHub](#login-with-github) guide.

## Configuring auth

The string form expands to the object form, which exposes every field:

```js
export default server({
  auth: {
    strategy: 'cookie',
    providers: ['google', 'github'],
    redirect: '/dashboard',
    users: redis.prefix('users:'),
    onUser: ({ password, internalId, ...user }) => user,
  },
});
```

| Field | Type | Description |
|-------|------|-------------|
| `strategy` | `'cookie' \| 'token' \| 'jwt'` | Required. How the session credential is issued and checked. See [cookie](#cookie-strategy), [token](#token-strategy) and [JWT](#jwt-strategy). |
| `providers` | `Provider[]` | OAuth providers and/or `email` to enable. |
| `redirect` | `string` | Where a `cookie` login redirects the browser; `'/user'` by default. |
| `users` | `Store` | One record per person; an in-memory `Map` by default. An OAuth user is keyed by its provider id, an email user by its email. |
| `onProfile` | `(raw, provider) => user` | Called during an OAuth login, when the provider returns its profile: maps the raw payload into your user. See [Callbacks](#callbacks). |
| `onLogin` | `(user, existing, ctx) => user` | Called on every login and registration, before anything is written: builds the record to store (the default upserts, fresh data wins); throw to deny. See [Callbacks](#callbacks). |
| `onUser` | `(user, ctx) => user` | Called on every authenticated request, and before a login response: shapes what `ctx.user` exposes (the default strips `password`). See [Callbacks](#callbacks). |
| `onToken` | `(user, ctx) => payload` | Called when a `jwt` login mints the token: builds the (client-readable) payload from the stored record; the default strips `password`. See [Callbacks](#callbacks). |
| `onLogout` | `(ctx) => void` | Called by `POST /auth/logout` after the session is revoked, with `ctx.user` still set. See [Callbacks](#callbacks). |

## Users and sessions

Auth builds on two stores with a clear split:

- **[`sessions`](#optionssessions)** (a root option): one record per device, the same [`ctx.session`](#ctxsession) every app has. Logging in stamps `user`, `provider` and `created` onto it, and the person is looked up on each request.
- **`auth.users`**: one record per person, keyed by the id the provider resolves. `ctx.user` is `users.get(ctx.session.user)`, shaped by [`onUser`](#callbacks).

The session data always lives in the store; what a strategy chooses is the **carrier**, how the session travels with each request:

| Strategy | Carrier | Session data |
|----------|---------|--------------|
| `cookie` | an `HttpOnly` cookie holding the session id | the `sessions` store |
| `token` | the same id, as an `Authorization: Bearer` header | the `sessions` store |
| `jwt` | the signed token itself carries the user | none: stateless, no `ctx.session` |

So `cookie` and `token` are one lifecycle with two transports, and [`jwt`](#jwt-strategy) opts out of session storage entirely. `users` is needed by every strategy: each login reads it for the existing-user upsert and persists the record; what `jwt` skips is only the per-request read.

Both stores default to in-memory `Map`s so development needs zero setup, and both are lost on restart, so in production auth refuses to boot without explicit stores:

```js
import server, { kv } from '@server/next';
import { createClient } from 'redis';

const redis = kv(createClient({ url: process.env.REDIS_URL }));

export default server({
  sessions: redis.prefix('session:'),
  auth: { strategy: 'cookie', providers: 'github', users: redis.prefix('users:') },
});
```

They don't need to share a backend: users in Postgres with sessions in Redis is the same shape, just two different stores. Auth only reads and writes single keys, so anything with a `get` and a `set` works; see [Your own store](#your-own-store).

## OAuth providers

Each provider reads its credentials from the environment:

| Provider | Env vars |
|----------|----------|
| `github` | `GITHUB_ID`, `GITHUB_SECRET` |
| `google` | `GOOGLE_ID`, `GOOGLE_SECRET` |
| `microsoft` | `MICROSOFT_ID`, `MICROSOFT_SECRET` |
| `discord` | `DISCORD_ID`, `DISCORD_SECRET` |
| `facebook` | `FACEBOOK_ID`, `FACEBOOK_SECRET` |
| `apple` | `APPLE_ID`, `APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY` |

Set each provider's authorized callback URL to `https://<your-host>/auth/callback/<provider>` for the server-owned flow, or to your app's own page for the client-owned one (see [Two OAuth flows](#two-oauth-flows)).

**Apple** signs its client secret as a short-lived ES256 JWT from `APPLE_PRIVATE_KEY`, and its callback is a `POST`.

## Two OAuth flows

Every OAuth provider supports two ways to run the handshake; pick per client, not per provider.

**Server-owned** (browsers, server-rendered apps, the `cookie` strategy). The server drives the redirects and validates a CSRF `state` bound to a short-lived cookie:

```
GET /auth/login/github  → 302 to GitHub (+ oauth_state cookie)
GitHub                  → GET /auth/callback/github?code&state
server checks the state → exchanges the code → logs in per strategy
```

Nothing to build; the earlier examples all use this flow.

**Client-owned** (SPAs, mobile and native apps, the `token`/`jwt` strategies). The app drives the redirect and the server only exchanges the code, no cookies involved:

```js
// 1. Ask for the authorize URL (JSON instead of a redirect)
const { url } = await (await fetch('/auth/login/github', {
  headers: { accept: 'application/json' },
})).json();
location.href = url;

// 2. GitHub returns to YOUR page (the registered redirect_uri) with ?code=...
// 3. Exchange it for the login
const res = await fetch('/auth/verify/github', {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({ code: new URLSearchParams(location.search).get('code') }),
});
const { token, ...user } = await res.json();
```

The JSON login accepts `redirect_uri`, `state` and `code_challenge` as query params and threads them into the authorize URL, so the app owns its own CSRF check (compare `state` on return) or uses PKCE; `/auth/verify/<provider>` passes `redirect_uri` and `code_verifier` through to the provider, which enforces them. The client secret never leaves the server.

`/auth/verify` responds per strategy: `201 { ...user, token }` for `token`/`jwt`, and for `cookie` a `201 { ...user }` with the session cookie attached, which fetch stores like any other, so an SPA can use HttpOnly cookie sessions too. Native Sign in with Apple works the same way: the SDK hands the app a `code`, and `POST /auth/verify/apple` accepts it (plus Apple's first-login `user` field).

## Email and password

The `email` provider keeps users in [`auth.users`](#users-and-sessions), with no third party. Passwords are hashed, never stored or returned in clear.

| Method | Route | Body | Notes |
|--------|-------|------|-------|
| `POST` | `/auth/register/email` | `{ email, password, ...fields }` | `email` must contain `@`, `password` ≥ 8 chars. Extra fields are stored on the user. The session is active on success. |
| `POST` | `/auth/login/email` | `{ email, password }` | |
| `PUT` | `/auth/password/email` | `{ previous, updated }` | Changes the password for the signed-in user. |

Register and login finish the session the same way as OAuth (a cookie or a token, per strategy).

## Cookie strategy

For browsers. Logging in stamps the auth fields onto the visitor's [session](#optionssessions), rotates its id into a fresh `HttpOnly` `session` cookie (`SameSite=Lax`, plus `Secure` in production), and redirects the browser to [`redirect`](#configuring-auth):

```js
export default server({ auth: 'cookie:github' })
  .get('/', (ctx) => ctx.user
    ? `Hi ${ctx.user.name}`
    : '<a href="/auth/login/github">Log in</a>');
```

The cookie carries only an opaque session id; the record lives in the `sessions` store and the user is looked up from it on each request. Browsers send the cookie automatically, so there's no client code to write. Log out with a form `POST` to `/auth/logout`, which deletes the whole session record (app data included) and clears the cookie.

To log a user out from the server side (a ban, a stolen laptop), delete their session records. Each one carries its `user`, so sweep the `sessions` store:

```js
for (const [id, session] of await sessions.entries()) {
  if (session.user === String(userId)) await sessions.del(id);
}
```

Their next request finds no session and comes through as anonymous. The same sweep, without the `del`, lists everywhere someone is signed in, with each session's `provider` and `created` date.

## Token strategy

For API clients and mobile apps. Login and register respond with JSON: the user, plus a `token` that is an opaque session id stored server-side. The client keeps it and sends it back on each request:

```js
export default server({ auth: 'token:email' });
```

```js
// On the client
const res = await fetch('/auth/login/email', {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({ email, password }),
});
const { token } = await res.json();

await fetch('/api/notes', { headers: { authorization: `Bearer ${token}` } });
```

The token is the same session id the cookie strategy stores, just carried in the `Authorization` header instead, so revocation works the same: `POST /auth/logout` with the bearer header ends that session, and the sweep shown [above](#cookie-strategy) logs a user out of every device at once.

## JWT strategy

For stateless APIs. Login responds like `token`, except the `token` is a signed JWT (HS256, with your [`secret`](#optionssecret)) **carrying the user itself**: the payload is the stored record shaped by [`onToken`](#callbacks) (which strips `password` by default), plus the provider and the standard `iat`/`exp` claims. A request presents the token, the signature is verified, and the claims become `ctx.user` through [`onUser`](#callbacks), with **no store reads at all**:

```js
export default server({ auth: 'jwt:email' });
```

Decode your own token and you'll find the same user object the login response carried. Two consequences to design for: the payload is **client-readable** (signed, not encrypted), so `onToken` is where you trim anything the user shouldn't see, and the claims are **frozen until the token expires** (one week), so a changed `name` or `roles` shows up on the next login, not the next request. Keep the user small; a big record means a big header on every request.

The statelessness is per request, not per login: each login still reads and writes [`users`](#users-and-sessions) (the existing-user upsert), so production requires it like every strategy. What `jwt` alone drops is `sessions`: there is no `ctx.session` at all, and any access to it throws. If you want bearer clients *with* server-side sessions, that's the [`token` strategy](#token-strategy).

`secret` **must** be set and stable: tokens are signed with it, so an unset per-process secret breaks every token on restart, and changing it invalidates all of them.

The flip side of statelessness is that there is nothing to delete: a token stays valid until it expires (one week), and `POST /auth/logout` only tells the client to discard it. To revoke earlier, keep your own denylist and check it in [`onUser`](#callbacks), which runs on every authenticated request:

```js
import server, { kv, ServerError } from '@server/next';

const store = kv(new Map());          // Redis in production
const revoked = store.prefix('revoked:');

export default server({
  auth: {
    strategy: 'jwt',
    providers: 'email',
    users: store.prefix('users:'),
    onUser: async ({ password, ...user }) => {
      if (await revoked.has(String(user.id))) {
        throw new ServerError('REVOKED', 401, 'Session revoked');
      }
      return user;
    },
    // a fresh login lifts the revocation
    onLogin: async (loginUser, existingUser) => {
      await revoked.del(String(loginUser.id));
      return { ...(existingUser ?? {}), ...loginUser };
    },
  },
});
```

Logging a user out of everything is then one write, from anywhere: `await revoked.set(String(userId), true)`. Two trade-offs to know: the check adds a store read to every request, handing back part of the statelessness; and the flag is per-user, not per-token, so once the user logs back in, previously issued tokens work again until they expire.

For machine-to-machine access with a single shared secret, no strategy is needed at all; see the [API keys](/tutorials/6-api-keys) tutorial.

## The user object

`ctx.user` is `undefined` when nobody is signed in. When present, every user carries `id`, `provider` and `strategy`; the rest depends on the provider:

| Provider | `ctx.user` |
|----------|-----------|
| OAuth (`github`, `google`, …) | `{ id, name, email, picture, provider, strategy }` |
| `email` | `{ id, email, ...fields, provider, strategy }` |

Type `ctx.user` with a second generic to `server()`; see [`ctx.user`](#ctxuser).

## Callbacks

Five callbacks cover the login lifecycle, named after the moment they fire (like [`onError`](#optionsonerror) and [`onResponse`](#optionsonresponse)). Each one **fully replaces** its built-in step, none of them runs "on top of" the default, and any user they return must carry an `id` and an `email` (a `500` otherwise). Deny a login by throwing:

```
OAuth callback
├─ provider payload arrives → onProfile(raw, provider)            → user
├─ stored user is read      → onLogin(loginUser, existingUser, ctx) → record
├─ the record is stored
└─ session issued (jwt: the token is minted → onToken(user, ctx) → payload)

every authenticated request
└─ user read from the store → onUser(user, ctx)                   → ctx.user
   (jwt: read from the verified token claims instead of the store)

POST /auth/logout           → onLogout(ctx)
```

| Callback | Signature | Returns | Fires |
|----------|-----------|---------|-------|
| `onProfile` | `(raw, provider)` | the mapped user | OAuth login only |
| `onLogin` | `(loginUser, existingUser, ctx)` | the record to store | every login |
| `onToken` | `(user, ctx)` | the `jwt` payload | `jwt` login only |
| `onUser` | `(user, ctx)` | the user to expose | login + every request |
| `onLogout` | `(ctx)` | nothing | logout |

### onProfile

Replaces the provider's built-in mapper, turning the raw OAuth payload into your user. The provider still does the token exchange and profile fetch; you only translate the result. For GitHub, `raw` is the `/user` response with `email` already resolved, so fields the built-in mapper drops (like the GitHub `login` username) are yours to keep:

```js
auth: {
  strategy: 'cookie',
  providers: ['github', 'google'],
  onProfile: (raw, provider) => {
    if (provider === 'github') {
      return { id: raw.id, email: raw.email, name: raw.name, username: raw.login };
    }
    return { id: raw.sub, email: raw.email, name: raw.name };
  },
},
```

One `onProfile` serves every configured provider, which is what the `provider` argument is for. It does not fire for `email`, since there's no provider payload to map. Some providers can omit the email (an Apple relay refusal, a phone-only Facebook account); the login then fails with a `500`, and `onProfile` is where you decide what to do instead, like synthesizing one from the provider id:

```js
email: raw.email ?? `${raw.id}@${provider}.local`,
```

### onLogin

Replaces the built-in upsert, building the exact record to persist from the fresh login and the stored user (`null` on a first login). The default merges the fresh data over the stored fields, so provider data wins. It runs **before** the record is written, so throwing denies the login without leaving an account behind:

```js
import { ServerError } from '@server/next';

auth: {
  strategy: 'cookie',
  providers: 'github',
  onLogin: async (loginUser, existingUser, ctx) => {
    if (!loginUser.email.endsWith('@company.com')) {
      throw new ServerError('NOT_ALLOWED', 403, 'Company accounts only');
    }
    if (!existingUser) await sendWelcome(loginUser);
    return {
      ...loginUser,
      ...existingUser,          // stored data wins instead of the default
      email: loginUser.email,   // except the email, always fresh
    };
  },
},
```

The returned record is stored verbatim, so with the `email` provider keep the `password` field on it, or nobody can log back in.

### onToken

`jwt` only. Builds the token payload from the stored record, once per login; the default strips `password`. The payload is **client-readable** (a JWT is signed, not encrypted) and frozen until the token expires, so this is where you decide what the token carries, independently of what [`onUser`](#onuser) later shows on `ctx.user`:

```js
auth: {
  strategy: 'jwt',
  providers: 'email',
  // The token carries only the identity core, however big the record gets
  onToken: ({ id, email, name }) => ({ id, email, name }),
},
```

The `provider` field is always re-added after the callback, and the payload must keep `id` and `email` (a `500` otherwise). Tokens whose claims lack them, including tokens issued before a payload change, are rejected with a `401`.

### onUser

Replaces the default shaping of what handlers see: it runs on **every** authenticated request before `ctx.user` is set, and before a login response body. Its input is the stored record, or under `jwt` the verified token claims (there is no store read). The default strips `password`. It can be async, so enriching from a database is fine:

```js
auth: {
  strategy: 'cookie',
  providers: 'github',
  onUser: async ({ password, ...user }, ctx) => ({
    ...user,
    permissions: await loadPermissions(user.id),
  }),
},
```

> [!WARNING]
> A custom `onUser` replaces the default instead of running after it, so drop `password` yourself as above. Leave it out and the stored hash ends up in `ctx.user` and in the login response.

### onLogout

An event fired by `POST /auth/logout`, after the session is revoked. `ctx.user` is still set for this last request:

```js
auth: {
  strategy: 'cookie',
  providers: 'github',
  onLogout: (ctx) => audit('logout', ctx.user.id),
},
```

## Protecting routes

Auth only verifies the credential and sets `ctx.user`; it never rejects a request on its own. Guard the routes you want to protect with a `ctx.user` check:

```js
const requireUser = (ctx) => {
  if (!ctx.user) return 401;
};

export default server({ auth: 'cookie:github' })
  .get('/public', () => 'anyone')
  .get('/account', requireUser,
    (ctx) => `Hello ${ctx.user.email}`);
```

## Responses

| Situation | Status |
|-----------|--------|
| No credential | anonymous (`ctx.user` is `undefined`) |
| Unknown or expired session id | anonymous (`ctx.user` is `undefined`) |
| Malformed Bearer credential, or a tampered JWT | `401` |
| Wrong email or password | `500` |
| Failed OAuth `state` check | `403` |

`POST /auth/logout` ends the session for `cookie`/`token`. Stateless `jwt` has nothing to revoke server-side (the client discards the token).

## Routes

| Method | Route | Provider |
|--------|-------|----------|
| `GET` | `/auth/login/<provider>` | OAuth. A `302` to the provider; with `Accept: application/json`, responds `{ url }` instead (see [Two OAuth flows](#two-oauth-flows)) |
| `GET` | `/auth/callback/<provider>` | OAuth (Apple `POST`) |
| `POST` | `/auth/verify/<provider>` | OAuth. Client-owned flow: exchanges `{ code, redirect_uri?, code_verifier? }` for a JSON login |
| `POST` | `/auth/register/email` | email |
| `POST` | `/auth/login/email` | email |
| `PUT` | `/auth/password/email` | email |
| `POST` | `/auth/logout` | all |
