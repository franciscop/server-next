# Authentication

The [`auth` option](#optionsauth) registers the login [routes](#routes) and populates [`ctx.user`](#ctxuser) on every request. It needs a [`store`](#optionsstore), and it never blocks a request on its own (see [Protecting routes](#protecting-routes)).

```js
server({ auth: 'cookie:github' });
server({ auth: { ...authOptions }});
```

For a step-by-step setup, see the [Login with GitHub](#login-with-github) guide.

## Configuring auth

The string form expands to the object form, which exposes every field:

```js
export default server({
  auth: {
    strategy: 'cookie',
    providers: ['google', 'github'],
    redirect: '/dashboard',
    store: users,
    session: sessions,
    onUser: ({ password, internalId, ...user }) => user,
  },
});
```

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `strategy` | `'cookie' \| 'token' \| 'jwt'` | *(required)* | How the session credential is issued and checked. See [cookie](#cookie-strategy), [token](#token-strategy) and [JWT](#jwt-strategy). |
| `providers` | `Provider[]` | `[]` | OAuth providers and/or `email` to enable. |
| `redirect` | `string` | `'/user'` | Where a `cookie` login redirects the browser. |
| `store` | `Store` | server `store`, `user:` prefix | Where users are kept. |
| `session` | `Store` | server `store`, `auth:` prefix | Where sessions are kept. |
| `onProfile` | `(raw, provider) => user` | per provider | Maps a provider's raw OAuth payload into your user. See [Callbacks](#callbacks). |
| `onLogin` | `(loginUser, existingUser, ctx) => user` | upsert, fresh wins | Builds the record to store; throw to deny the login. See [Callbacks](#callbacks). |
| `onUser` | `(user, ctx) => user` | strips `password` | Shapes the user exposed on `ctx.user` and login responses. See [Callbacks](#callbacks). |
| `onLogout` | `(ctx) => void` | *(none)* | Event fired when a session is revoked. See [Callbacks](#callbacks). |

## Users and sessions

Auth uses two key-value stores, both derived from your [`store`](#optionsstore) by default:

- **Users**: the `user:` prefix. An OAuth user is keyed by its provider id, an email user by its email.
- **Sessions**: the `auth:` prefix, lasting a week. The cookie or bearer token is only a session id; the user is looked up from it on each request.

## OAuth providers

Each provider reads its credentials from the environment:

| Provider | Env vars |
|----------|----------|
| `github` | `GITHUB_ID`, `GITHUB_SECRET` |
| `google` | `GOOGLE_ID`, `GOOGLE_SECRET` |
| `microsoft` | `MICROSOFT_ID`, `MICROSOFT_SECRET` |
| `discord` | `DISCORD_ID`, `DISCORD_SECRET` |
| `facebook` | `FACEBOOK_ID`, `FACEBOOK_SECRET` |
| `apple` | `APPLE_ID`, `APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY` |

Set each provider's authorized callback URL to `https://<your-host>/auth/callback/<provider>`. The flow is CSRF-protected with a short-lived `state` cookie.

**Apple** signs its client secret as a short-lived ES256 JWT from `APPLE_PRIVATE_KEY`, and its callback is a `POST`.

## Email and password

The `email` provider keeps users in your [`store`](#optionsstore), with no third party. Passwords are hashed, never stored or returned in clear.

| Method | Route | Body | Notes |
|--------|-------|------|-------|
| `POST` | `/auth/register/email` | `{ email, password, ...fields }` | `email` must contain `@`, `password` ≥ 8 chars. Extra fields are stored on the user. The session is active on success. |
| `POST` | `/auth/login/email` | `{ email, password }` | |
| `PUT` | `/auth/password/email` | `{ previous, updated }` | Changes the password for the signed-in user. |

Register and login finish the session the same way as OAuth (a cookie or a token, per strategy).

## Cookie strategy

For browsers. Logging in sets a signed, `HttpOnly` `authentication` cookie (`SameSite=Lax`, plus `Secure` in production) and redirects the browser to [`redirect`](#configuring-auth):

```js
export default server({ store: new Map(), auth: 'cookie:github' })
  .get('/', (ctx) => ctx.user
    ? `Hi ${ctx.user.name}`
    : '<a href="/auth/login/github">Log in</a>');
```

The cookie carries only an opaque session id; the session lives in the [session store](#users-and-sessions) for a week and the user is looked up from it on each request. Browsers send the cookie automatically, so there's no client code to write. Log out with a form `POST` to `/auth/logout`, which deletes the session and clears the cookie.

To log a user out from the server side (a ban, a stolen laptop), delete their session records. Sessions are keyed by session id with the user inside, so sweep the `auth:` prefix of your store:

```js
const sessions = store.prefix('auth:');
for (const [id, session] of await sessions.entries()) {
  if (session.user === String(userId)) await sessions.del(id);
}
```

Their next request finds no session and comes through as anonymous.

## Token strategy

For API clients and mobile apps. Login and register respond with JSON: the user, plus a `token` that is an opaque session id stored server-side. The client keeps it and sends it back on each request:

```js
export default server({ store: new Map(), auth: 'token:email' });
```

```js
// On the client
const res = await fetch('/auth/login/email', {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({ email, password }),
});
const { token } = await res.json();

await fetch('/api/notes', { headers: { authorization: `Bearer ${token}` } });
```

Sessions are the same server-side records as the cookie strategy (a week, in the [session store](#users-and-sessions)), so revocation works the same: `POST /auth/logout` with the bearer header ends that session, and the sweep shown [above](#cookie-strategy) logs a user out of every device at once.

## JWT strategy

For stateless APIs. Login responds like `token`, except the `token` is a signed JWT (HS256, with your [`secret`](#optionssecret)) carrying the session itself. Nothing is stored server-side, so requests can be verified without a shared session store:

```js
export default server({ store: new Map(), auth: 'jwt:email' });
```

`secret` **must** be set and stable: tokens are signed with it, so an unset per-process secret breaks every token on restart, and changing it invalidates all of them.

The flip side of statelessness is that there is nothing to delete: a token stays valid until it expires (one week), and `POST /auth/logout` only tells the client to discard it. To revoke earlier, keep your own denylist and check it in [`onUser`](#callbacks), which runs on every authenticated request:

```js
import server, { kv, ServerError } from '@server/next';

const store = kv(new Map());          // Redis in production
const revoked = store.prefix('revoked:');

export default server({
  store,
  auth: {
    strategy: 'jwt',
    providers: 'email',
    onUser: async ({ password, ...user }) => {
      if (await revoked.has(String(user.id))) {
        throw new ServerError('REVOKED', 401, 'Session revoked');
      }
      return user;
    },
    // a fresh login lifts the revocation
    onLogin: async (loginUser, existingUser) => {
      await revoked.del(String(loginUser.id));
      return { ...(existingUser ?? {}), ...loginUser };
    },
  },
});
```

Logging a user out of everything is then one write, from anywhere: `await revoked.set(String(userId), true)`. Two trade-offs to know: the check adds a store read to every request, handing back part of the statelessness; and the flag is per-user, not per-token, so once the user logs back in, previously issued tokens work again until they expire.

For machine-to-machine access with a single shared secret, no strategy is needed at all; see the [API keys](/tutorials/api-keys) tutorial.

## The user object

`ctx.user` is `undefined` when nobody is signed in. When present, every user carries `id`, `provider` and `strategy`; the rest depends on the provider:

| Provider | `ctx.user` |
|----------|-----------|
| OAuth (`github`, `google`, …) | `{ id, name, email, picture, provider, strategy }` |
| `email` | `{ id, email, ...fields, provider, strategy }` |

Type `ctx.user` with a second generic to `server()`; see [`ctx.user`](#ctxuser).

## Callbacks

Four callbacks cover the login lifecycle, named after the moment they fire (like [`onError`](#optionsonerror) and [`onResponse`](#optionsonresponse)). Each one **fully replaces** its built-in step, none of them runs "on top of" the default, and any user they return must carry an `id` and an `email` (a `500` otherwise). Deny a login by throwing:

```
OAuth callback
├─ provider payload arrives → onProfile(raw, provider)            → user
├─ stored user is read      → onLogin(loginUser, existingUser, ctx) → record
├─ the record is stored
└─ session issued

every authenticated request
└─ user read from the store → onUser(user, ctx)                   → ctx.user

POST /auth/logout           → onLogout(ctx)
```

| Callback | Signature | Returns | Fires |
|----------|-----------|---------|-------|
| `onProfile` | `(raw, provider)` | the mapped user | OAuth login only |
| `onLogin` | `(loginUser, existingUser, ctx)` | the record to store | every login |
| `onUser` | `(user, ctx)` | the user to expose | login + every request |
| `onLogout` | `(ctx)` | nothing | logout |

### onProfile

Replaces the provider's built-in mapper, turning the raw OAuth payload into your user. The provider still does the token exchange and profile fetch; you only translate the result. For GitHub, `raw` is the `/user` response with `email` already resolved, so fields the built-in mapper drops (like the GitHub `login` username) are yours to keep:

```js
auth: {
  strategy: 'cookie',
  providers: ['github', 'google'],
  onProfile: (raw, provider) => {
    if (provider === 'github') {
      return { id: raw.id, email: raw.email, name: raw.name, username: raw.login };
    }
    return { id: raw.sub, email: raw.email, name: raw.name };
  },
},
```

One `onProfile` serves every configured provider, which is what the `provider` argument is for. It does not fire for `email`, since there's no provider payload to map. Some providers can omit the email (an Apple relay refusal, a phone-only Facebook account); the login then fails with a `500`, and `onProfile` is where you decide what to do instead, like synthesizing one from the provider id:

```js
email: raw.email ?? `${raw.id}@${provider}.local`,
```

### onLogin

Replaces the built-in upsert, building the exact record to persist from the fresh login and the stored user (`null` on a first login). The default merges the fresh data over the stored fields, so provider data wins. It runs **before** the record is written, so throwing denies the login without leaving an account behind:

```js
import { ServerError } from '@server/next';

auth: {
  strategy: 'cookie',
  providers: 'github',
  onLogin: async (loginUser, existingUser, ctx) => {
    if (!loginUser.email.endsWith('@company.com')) {
      throw new ServerError('NOT_ALLOWED', 403, 'Company accounts only');
    }
    if (!existingUser) await sendWelcome(loginUser);
    return {
      ...loginUser,
      ...existingUser,          // stored data wins instead of the default
      email: loginUser.email,   // except the email, always fresh
    };
  },
},
```

The returned record is stored verbatim, so with the `email` provider keep the `password` field on it, or nobody can log back in.

### onUser

Replaces the default shaping of what handlers see: it runs on the stored user before it becomes `ctx.user`, on **every** authenticated request, and before a login response body. The default strips `password`. It can be async, so enriching from a database is fine:

```js
auth: {
  strategy: 'cookie',
  providers: 'github',
  onUser: async ({ password, ...user }, ctx) => ({
    ...user,
    permissions: await loadPermissions(user.id),
  }),
},
```

> [!WARNING]
> A custom `onUser` replaces the default instead of running after it, so drop `password` yourself as above. Leave it out and the stored hash ends up in `ctx.user` and in the login response.

### onLogout

An event fired by `POST /auth/logout`, after the session is revoked. `ctx.user` is still set for this last request:

```js
auth: {
  strategy: 'cookie',
  providers: 'github',
  onLogout: (ctx) => audit('logout', ctx.user.id),
},
```

## Protecting routes

Auth only verifies the credential and sets `ctx.user`; it never rejects a request on its own. Guard the routes you want to protect with a `ctx.user` check:

```js
const requireUser = (ctx) => {
  if (!ctx.user) return 401;
};

export default server({ store, auth: 'cookie:github' })
  .get('/public', () => 'anyone')
  .get('/account', requireUser,
    (ctx) => `Hello ${ctx.user.email}`);
```

## Responses

| Situation | Status |
|-----------|--------|
| No credential | anonymous (`ctx.user` is `undefined`) |
| Invalid or expired token / cookie | `401` |
| Wrong email or password, or an unverifiable JWT | `500` |
| Failed OAuth `state` check | `403` |

`POST /auth/logout` ends the session for `cookie`/`token`. Stateless `jwt` has nothing to revoke server-side (the client discards the token).

## Routes

| Method | Route | Provider |
|--------|-------|----------|
| `GET` | `/auth/login/<provider>` | OAuth |
| `GET` | `/auth/callback/<provider>` | OAuth (Apple `POST`) |
| `POST` | `/auth/register/email` | email |
| `POST` | `/auth/login/email` | email |
| `PUT` | `/auth/password/email` | email |
| `POST` | `/auth/logout` | all |
